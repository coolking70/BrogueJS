# 开发指南

## 1. 环境

- Node.js 20+（开发时使用 Node 22），npm。
- 首次克隆：

```bash
npm ci
npm run dev             # 本地开发服务器
```

常用命令：

| 命令 | 作用 |
|---|---|
| `npm run dev` | Vite 开发服务器 |
| `npm run build` | 类型检查（vue-tsc）+ 生产构建，产物在 `dist/` |
| `npm test` | 常规测试（不含重型生成普查、生成基线）；没有 CE 参照源码时，CE 对照用例显式跳过 |
| `npm run test:full` | CE 一致性检查：同上，但**要求** CE 参照源码存在（缺失即失败），常规组 CE 对照用例全部运行 |
| `npm run test:gen` | 重型生成普查；需要强制 CE 对照时用 `BROGUE_REQUIRE_CE=1 npm run test:gen` |
| `npm run test:drift` | 地图生成回归基线 |
| `npx vue-tsc -b` | 仅类型检查 |

## 2. CE 参照源码（可选）

轻/中档开发与验收不需要 CE 源码。大部分测试（真实入口端到端、生成合理性、录像回放、目录全集、黄金 trace）不依赖它。少量"CE 对照"：从 CE C 源码提取函数编译成参照程序比对、核对目录表、校验行号引用。这些需要 CE 源码，但本仓库不收录它：

```bash
npm run ce:fetch                          # 默认 legacy：BrogueCE-chs 固定提交里的 BrogueCE-master/src（测试按此版本编写）
npm run ce:fetch -- --source upstream     # 最新官方 tmewett/BrogueCE（可能与测试引用的行号/中文化改动不一致）
npm run ce:fetch -- --force               # 重新拉取
```

也可以设置环境变量 `BROGUE_CE_DIR` 指向任意一份 CE 源码目录（其下应有 `src/brogue/`）。

legacy 版本是 CE 1.x 源码加上本项目早期（C 版）中文化改动；测试里引用的 `Movement.c:1297` 这类行号都以它为准。**核对规则时应同时对照官方最新 CE**；两者在规则上不应有差别，有差别时请记录。

## 3. 工作流：任务书 → 执行 → 验收

之前的开发一直采用"执行方 / 验收方"分离，换了人或工具也建议保留：

1. **任务书**（`docs/tasks/<id>.md`）：写清规格来源（CE 出处或勘察报告条目）、修改范围（哪些文件/方法段可以改）、约束、门禁档位、报告要求。
2. **执行**：在独立工作树（git worktree）里改代码、补守卫、跑门禁、写报告，不直接提交主分支。
3. **验收**：
   - 抽查 CE 事实（**读执行路径，不读注释**——注释多次写错过）；
   - 审核"旧守卫前提修订"（见 §5）；
   - 审核生成基线/黄金 trace 的重录是否有单变量归因；
   - 合并后若主分支已有其它改动，按档位在合并结果上补跑门禁；
   - 提交、推送。

合并用补丁三方合并，不要整文件覆盖（整文件拷贝会抹掉中间已合并的改动）：

```bash
# 在执行方工作树
git add -A && git diff --cached --binary HEAD > /tmp/unit.patch && git reset
# 在主仓
git apply -3 /tmp/unit.patch
git diff --name-only --diff-filter=U           # 冲突文件
grep -rln '^<<<<<<<\|^>>>>>>>' src scripts     # 必查：-3 可能静默留下冲突标记
```

翻译 JSON 冲突通常是两边各加了键：保留两边，注意逗号，并用 `JSON.parse` 验证。

## 4. 门禁分档

| 档位 | 适用 | 内容 |
|---|---|---|
| 轻 | 纯前端（组件、样式、界面文案、只读显示） | `vue-tsc -b` + `build` + 相关前端测试 + **所有读源码守卫** |
| 中 | 引擎里不改规则的部分（消息、显示、日志、自动行动流程、输入） | 轻档 + 相关单测 + UR2/UR3/UR4 黄金 trace + 录像测试（u_27、x2a、x3b）+ U03 契约 + `test:drift` |
| 局部规则 | 只改战斗、物品效果、状态、AI 等局部规则；不改生成、随机数消耗次数/顺序、存档或录像格式 | 中档 + 与改动相关的全部测试 + `test:full`（不含重型生成普查）+ `test:drift` |
| 全量 | 改地图/物品/怪物生成、随机数消耗、存档/录像格式；同步新版 CE；打版本标签前 | `vue-tsc -b` + `build` + `test:full` + `BROGUE_REQUIRE_CE=1 npm run test:gen` + `test:drift` |

- **打版本标签前必须全量兜底一次。** 局部规则/全量档先 `npm run ce:fetch` 准备参照源码；`test:full` 缺 CE 即失败。全量档的普查也强制要求 CE，避免对照用例被跳过。
- 三套文件归属由 `scripts/test-suites.json` 唯一定义：常规（含 `test:full`）、重型生成普查、生成基线互不重叠。新增测试必须登记；普查以实测耗时和执行内容判定，不能只按文件名分类。
- "读源码的守卫"（扫描源码的测试）轻/中档也必须跑：`c_4a_terrain_catalog`（mechFlags 读者白名单）、`p1_30_i18n_gate`、`u24_hardcoded_text`、`repo_hygiene`、`test_suite_membership` 等。曾两次只在全量里才暴露白名单问题。若文件归入 `test:gen`，仍须用 `npx vitest run <文件> -t '<守卫用例名>'` 跑其中的源码守卫；直接定向运行不受 npm 套件排除影响。
- 长普查测试（如 `blueprint_center`、`b2_transcription`、`v_2b_7_features`）在 CPU 争用下容易超时：按原门限、单 worker 单独复跑确认，不改超时、种子或断言。保留原完整命令的退出码；串行复核通过不能冒充完整套件一次全绿。
- 跳过全量复跑的条件（三条同时满足）：主分支自执行方开工后没变（只允许有纯文档提交）、验收方没改任何文件、执行方的全量三套命令（`test:full`、强制 CE 的 `test:gen`、`test:drift`）均完整跑完全绿（不是中止或定向拼接）。

## 5. 验收裁决规则

- **CE 优先**：任务书、旧测试与 CE 冲突时，以 CE 为准，并把任务书的错误写进裁决记录（例：长休息上限任务书写 100，CE 为需恢复时 300）。
- **撞上守卫时改代码，不改守卫。**
- **旧守卫前提修订**（只有在旧测试依赖被修掉的旧行为时才允许）：必须先做**单变量反事实**——只回退本单元的生产文件，原测试应当通过；恢复新代码，原测试失败。然后只改测试的前提（观察时点、布景、夹具、历史计数），**不改断言语义、不放宽容差、不删用例、不加 skip**。验收方逐条裁决。
- **翻转期望**（把断言改成相反）只在有 CE 出处时允许。
- **生成基线 / 黄金 trace 重录**：先单变量归因（只回退本单元生产文件，旧夹具应精确复现），再用原捕获方法重录，逐字段登记变化原因。归因不清不许重录。
- 项目决策（不做逐骰一致、不做迁移等）见 `docs/ce-alignment.md` §3，不在验收时重新讨论。

## 6. 勘察（只读审查）

规则层之外，缺陷常藏在"交互/自动行动/消息"和"内容完整性"里（X-3、X-4 两轮都由试玩触发）。做勘察时：

- 以 CE 源码为清单逐项对照（如按键表 `executeKeystroke`、全部 `rogue.disturbed = true`、全部 `message`/`flavorMessage`/`confirm` 调用、各目录枚举全集）。
- 每条差异给出 CE 与 web 的 `文件:行`，分级（S1 影响游玩决策/安全、S2 明显偏差、S3 细节），给出修复单元分组与门禁档位。
- 能写探针实测的就实测（生成普查跑足够多种子，统计"CE 应有但 web 为 0"的内容——血根草、藻井、营地都是这样找到的）。
- 勘察不改源码；探针放未跟踪临时目录，结论写报告。

勘察报告范例：`docs/archive/dev-history/reports/x-3-survey.report.md`、`x-4-survey.report.md`。

## 7. 常见坑

- 单跑测试要在仓库根执行（部分守卫按相对路径读源码，在别处运行会 ENOENT 假失败）。
- 不要把"推送"和"跑测试"写在同一条命令里：先看测试结果，再单独推送。
- 文件列表循环写到文件再 `while IFS= read -r`，别依赖 shell 拆分变量（zsh 不按空格拆）。
- `grep -c` 无匹配时退出码为 1，别把它串在 `&&` 前面决定是否提交。
- 提交用显式路径，避免把未验收的改动扫进去。
- 新增只读显示逻辑也可能动到 RNG（例如调用了带随机的格式化函数）：审计 RNG 调用点。
- 大体积原始证据（>1 MB）、截图不进仓库；报告里写明本地位置即可。
- 不产生 CRLF（Windows 执行环境注意）。

## 8. 代码约定

- 规则代码旁注明 CE 出处（`Movement.c:1297-1308` 这类），便于核对；但**以执行路径为准**，注释可能过时。
- 纯函数优先，副作用经 ports 注入；显示函数不消耗实质随机流。
- 所有玩家可见文本走 i18n（见 `docs/i18n.md`）。
