# 设计：统一的界面内弹窗层（替代原生 window.confirm，并修正"--更多--"与多回合推进的时序）

> 本步**只做盘点与设计文档，不改生产代码**。工作区 `BrogueJS-ext`（detached，基于 main `1ff39a8`）。用户已同意此方向，设计经维护者确认后另行实施。
> 证据录像：`.tmp-evidence/brogue-web-replay-1791020631948.json`（种子 438319328，普通模式，3744 条命令，不入库）。

## 背景与已确认的问题

### A. 原生确认框
`src/App.vue` 中 `wireConfirmRequest` 用同步 `window.confirm()` 实现引擎的 `requestConfirm`（对应 CE IO.c confirm() 同步等待）。问题：
- 原生模态冻结页面并吞掉指针事件，已导致"按住方向键遇确认框后反复弹窗"（已用 heldInput 规避，但根因仍在）
- 样式、按键、移动端体验无法控制
- 自动化浏览器无法读取/操作原生对话框：扩展分支 1d/1e 两次无法验证"取消"分支

### B. "--更多--"（REQUIRE_ACKNOWLEDGMENT）在多回合推进中的时序
Claude 用上述录像重放确认：玩家在第 3371 回合发出一条 `move 0`，同一条命令内推进到第 3383 回合死亡（录像回放无 OOS，规则结果合法）。期间消息依次为：
`[ACK] a pressure plate clicks underneath Goblin conjurer!` → `paralytic gas sprays…` → `[ACK] You are paralyzed!`（麻痹 19 回合）→ 幽灵之刃连续攻击 → 死亡。
用户体验为"麻痹中弹窗卡住，然后死亡"。`src/engine/Systems/Logger.ts` 注明 acknowledgement 只是 presentation-only，模拟推进并不等待确认；CE 中 `--MORE--` 会阻塞，确认后再逐回合演示麻痹期间的推进。需查明 JS 版在推进/动画期间：确认层是否可交互、推进是否应暂停、死亡结算画面是否被确认层遮挡/阻断。

## 设计要求（写入 `docs/design/in-app-dialogs.md`）
1. **统一弹窗层**：一个界面内、覆盖在游戏上方的对话层服务，至少支持：确认（是/否，可配置默认项与危险样式）、需要确认的消息（--更多--，可连续排队）、以及为将来对话/剧情预留的扩展类型；键盘（含 CE 键位 y/n/Esc/空格等）、鼠标、触摸一致；可被自动化测试稳定读取与操作。
2. **确认的异步化方案**：评估并推荐其一（或组合）：
   - 方案一"预检-中止-重放"：在状态改动/掷骰之前遇到确认时中止本条命令（不改状态、不消耗 RNG、不记录），弹出界面确认，用户选择后以**带决策**的同一命令重新执行（复用录像现有 decisions 机制，回放语义不变）；
   - 方案二"生成器挂起"：利用推进循环已有的 generator/yield，在确认点挂起命令；
   - 其它方案。
   对每个 requestConfirm 调用点说明所推荐方案是否成立；不成立的给出单独处理。必须保证：录像/存档格式与回放决策语义不变或给出明确迁移说明；经典 CE 行为不变；黄金 trace 不变。
3. **"--更多--"与推进时序**：给出与 CE 一致的呈现方案——需要确认的消息出现时暂停推进演示（或将后续推进演示排在确认之后），确认后继续；确认层在任何推进/动画状态下都可交互；游戏结束画面不被确认层阻断；说明对 animationEnabled 开/关、自动行进、回放播放/seek 的处理。注意这是呈现层：模拟结果与 RNG 必须与现在完全一致。
4. **测试与验收计划**：自动化（组件/引擎/录像）测试清单，以及可由浏览器自动化稳定执行的验收步骤（包括"确认框取消不扣费不耗时不耗 RNG"、上述录像场景的重现）。
5. **影响与分步实施计划**：对 main 与扩展分支（ext/foundation，有大量 UI 与 1d 受控动作确认）的影响、冲突风险与建议的合并顺序；分步实施拆分及每步门禁档位（docs/development.md §4）。
