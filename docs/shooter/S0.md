依据 2026-10-05 的 BJS-SHOOTER-001 RFC，只实施 S0。当前交付是实时运行时和两角色诊断场，等待维护者验收；尚不是可玩的射击关卡。

## 运行

```bash
npm ci
npm run dev -- --host 0.0.0.0
# 打开 Vite 输出地址下的 /shooter.html
```

`npm run build` 同时输出原入口 `dist/index.html` 和独立入口 `dist/shooter.html`。`npm run preview` 后也可使用 `/shooter.html`。未改 `main.ts`、`GameCanvas.vue` 或原游戏的启动/输入逻辑。

页面支持：实时运行、暂停、单 Tick 步进、手动诊断动作、指定种子重开、保存/恢复检查点、录像导入/导出，以及暂停后重新执行当前输入历史的验证。后台自动暂停，回到前台需要手动继续。

两角色保持静止：手动角色通过 InputFrame 发起动作；自动角色每 60 Tick 决策一次。动作的每个结算段从独立引擎 RNG 抽取一个诊断数值，因而测试可以检查真实随机流顺序与完整内部状态，不能仅比较 Tick 计数。圆环、光圈和时间游标只读机械快照。

## 时间合同

- 产品：`shooter-s0`，版本 1；Simulation：`shooter-realtime-30`，固定 30 Hz。
- 浏览器只向 Driver 提供 `Math.round(rAF 时间戳 × 1000)`。使用**绝对单调微秒时间戳**，不能先将每帧 delta 取整再累加。
- Driver 累积 `微秒 × Hz` 的整数 credit，每 1,000,000 credit 对应一个 Tick。机械核心只接收连续的 Tick 输入，不读取 rAF、Date、performance 或 Pixi ticker。
- 每次 pump 最多 8 Tick；剩余债务保留，并通过 `backlogTicks` 暴露。不会丢 Tick 或降低模拟频率掩盖卡顿。存在积压时 alpha 固定为 1，避免外插。
- pause 保留已挣得的 credit，清除墙钟锚点；resume 的第一次 pump 只重设锚点，暂停期间不产生补算债务。重复 resume 不重置正在运行的锚点。
- 输入/决策先提交，再推进动作 1 Tick，然后按 owner ID 结算到期段，最后发布快照。动作从 Tick 1 发起、前摇 6 Tick 时在 Tick 6 结算。
- 忙碌时触发的手动动作会作为输入记录但不排队。连续渲染帧不消费输入边沿。
- Tick 或调度回调发生未回滚异常后停止运行，不能继续产生看似有效的录像。

`ActorActionScheduler` 的生产实现未改。它仍是动作阶段倒计时唯一所有者；`ticksUntilTurn` 只作为它维护的镜像。S0 没有把 Brogue 的 `movementSpeed=100` 换算成现实时间，也不调用 `executeCommand('wait')` 伪装实时推进。

## 独立状态与录像

Snapshot 包含专有 format/version、product/simulation、频率、空模块 manifest、seed、tick、action ID、两个 actor、完整 ActorActionScheduler 状态和完整双 RNG 状态。与原 Brogue 保存格式互不加载，不做旧档迁移。

Replay 包含专有 format/version、初始完整 checkpoint、逐 Tick InputFrame 和最终完整 checkpoint。通过同一 `advanceTick` 重新执行输入，以规范键序 JSON 比较全部机械状态；时间戳、暂停和渲染帧不入录像。

恢复检查点后，以该检查点为新录像起点。界面明确说明此行为，不宣称保留恢复点之前的录像来源。重放先构造新 Session，通过全部验证后才替换当前局；校验失败保留原局。

S0 为诊断用途，最多 108,000 Tick（一小时）。每 Tick 保存一条 InputFrame，尚未做压缩、网络、周期检查点或历史 seek。S0 的 move/aim 字段保留协议形状但拒绝非零值，不把未实现的空间能力当作有效输入。随机种子须为显式非零 uint32。

## 验证入口

```bash
NODE_OPTIONS=--max-old-space-size=3072 npx vitest run \
  src/test/shooter_realtime_clock.test.ts \
  src/test/shooter_frame_independence.test.ts \
  src/test/shooter_replay_clock.test.ts --maxWorkers=2

NODE_OPTIONS=--max-old-space-size=3072 node scripts/check-shooter-s0.mjs \
  --output ../shooter-s0-evidence
```

浏览器脚本需要 Playwright Chromium；可通过 `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` 指定已安装的 Chromium。`--engine-only` 明确跳过浏览器，不能视为浏览器通过。报告与截图写在仓库外。该脚本使用**模拟的** 600 秒输入测试，不冒充真实墙钟连续十分钟的浏览器烧机。

新增测试登记在仓库默认测试清单；覆盖精确阶段边界、计时精度、pause/resume、积压保留、异常停止、重复/非法输入、600 秒状态相等、多 Session 隔离、存读档的每种动作阶段、录像篡改和版本拒绝。原模块组合 smoke 仍使用真实 Game 入口，独立于 S0 诊断场。

实际门禁结果见 [S0 验证报告](S0-report.md)。

## 尚未证明与下一阶段边界

- 当前接入的是正式 ActorActionScheduler 和 Random，不是整个 `Game` 世界。地形环境、原怪物 AI、饥饿、主观回合效果及已有模块生命周期没有被接入实时 Session。
- `TimeCoordinator` 的原回合推进入口保持原状；尚未统一成一个形式上的 `TurnSimulationDriver` 包装器，以免空包装让读者误以为两种世界已经完全共享。
- 模块 manifest 当前为空，版本拒绝已建立；Growth/Narrative/Giants 的实时运行并未验收。
- 性能场景只有两个静止诊断角色，不代表 200 个 Horde Unit、Boss 或移动端实机性能。
- S1 前需要先确定 Grid 环境进入实时世界的客观频率与效果归属，再加入连续位置与碰撞；不能让它们继续借用玩家回合推进。
- 本轮没有实现连续移动、枪械、任务、尸潮、战略层或联机。S0 验收后再按 RFC 进入 S1。
