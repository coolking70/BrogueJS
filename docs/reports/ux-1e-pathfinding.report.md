## 结论与范围

纯网格受控样本确认旧 A* 的开放节点维护有优化价值；改为稳定索引二叉堆后，较长搜索样本的中位耗时改善约 2.1–6.1 倍，短邻格搜索没有明显回退。旧路径、回调调用顺序和双 RNG 状态保持一致。

这不是自然 D4 卡顿复现，也不是完整游戏帧率/长任务改善的证据。未生成地牢、未启动完整游戏或浏览器、未跑深层采样与重门禁；后台基线重测未受操作干预。主线程仍需在空闲环境用完整应用对 D3–5 做采样，确认实际瓶颈占比。

## 测量先行

先冻结旧生产 `Pathfind.ts` 为独立 oracle `src/test/support/legacyPathfind.ts`，只修改导入路径和类名。旧实现每次取节点都扫描完整 openSet 取最低 f，又在线性数组中检查邻居是否已开放并 splice 删除。网格不可达时仍会做完整可达区域搜索。

在修改生产前，运行 `node scripts/ux-1-path-profile.mjs`：实际旧生产与冻结 oracle 的路径、canPass 次数相同；两者时间比约 0.98–1.02，确认同一测量方式没有算法版本偏置。79×29 的不可达屏障场景约 5.1ms/次，曲折通道约 2.8–2.9ms/次，均不包含世界生成和渲染。

脚本仅加载两个纯算法模块，禁用 Vite dependency scan，不监听网络端口。每场景先预热，再交替旧/新算法的执行先后；9 批，每批 8 次。报告的中位/p95 是“每批平均单次耗时”分布，**不是浏览器单帧延迟的 p95**。

## 实现与等价条件

`Pathfind.ts` 的唯一算法变更是把 openSet / fScore 维护交给 `PathFrontier.ts`：

- 先比较完全相同的 f；f 严格相等时按当前开放期间的插入序号排序，与旧数组第一次遇到最低 f 的规则一致。
- decrease-key 保留已有开放节点的序号和原 Pos 对象；不能通过重新入队改变平分顺序。
- 已弹出节点被重新打开时获得新序号，等价于旧数组尾部 push。
- 原 dx 外层 / dy 内层邻居次序、goal 预检查、isValidPos/canPass/canStep 的调用条件与次序全部保留。
- 保留 1.414 的斜向移动代价、原启发函数数值及严格 g 改善判断；没有借性能修复之名更改代价或规则。
- 队列索引和序号只在一次寻路内部存活，不进 Game、存档、录像；不增加 RNG 调用。回调收到的仍是纯 `{x,y}`，不暴露堆 metadata。

查找现存开放节点由线性扫描变为 Map；弹出和 decrease-key 为 O(log F)，F 为开放节点数。

## 独立行为对照

`src/test/ux_1e_pathfinding.test.ts`：5 用例全过，整个文件约 0.44 秒（算法断言约 0.23 秒）。覆盖：

- 4000 次插入、降分、弹出混合操作，与独立有序数组逐个比较对象身份和队列大小。
- 直接构造同 f / decrease-key / reopen，确认保持原位置对象，降分不改变原插入优先级，重开改为队尾优先级。
- 3×3 全部 512 障碍掩码 × 双向起终点 × 有/无斜向移动，2048 个场景。
- 600 个不同尺寸/障碍分布的小网格，各自再跑普通与动态回调版本，共 1200 场景。动态回调按调用次数开关通行和 canStep，检验调用顺序本身而不只看最终路径。
- 每个场景比较完整路径、每次边界检查/通行/跨格回调的坐标、结果与先后，包含不可达目标。额外覆盖同点、越界目标、阻塞目标和回调异常。
- 对照前后检查两条 RNG 的状态与计数完全相同。

没有修改现有测试断言、超时、基线或黄金 trace，不涉及旧守卫前提修订。
