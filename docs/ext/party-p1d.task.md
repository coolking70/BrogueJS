## 2 不变量与实现要求

### 2.1 动态名册与转换事务

- 上限仍 4 名在籍成员，留守计入；死亡历史与在籍计数按 §8 PD1 明确定义。`primaryActorId` 和 `Game.player` 保持开局主实体；leader 可显式移交，focus 仅显示。成员只有一个实体/层/调度/库存权威根，不通过复制 Player 或临时交换 game.player 转换。
- 当前 P1a 联合准入把 roster 与不可变 `manifest.configuration.party.members` 关联。该值以后表示开局人数，不能随招募改 manifest 或删掉人数检查：实现经批准的动态成员来源/生命周期记录与严格联合验证，证明当前名册从合法开局及转换事件产生；无来源诊断档仍需完整实体图校验，不能仅依赖 recordingOrigin。
- 三类来源共用 foundation 的受信任资格/转换能力口，party 负责招募政策和 UI；narrative/settlement 通过可选能力传递权威来源，不交叉 import 模块实现。禁止 payload 自报“已解救/剧情已批准/居民已解除”绕过真实世界根；公共输入经 `game.executeCommand` / `executeItemCommand`，严校 actorId、来源实体、level、expectedRevision、issuerSlot 与目标营地，不能递归 executeCommand。
- 接受前整体预检：本地管理权限、来源资格、同层合法接触、容量、唯一实体、单格、存活、非 raid/临时/敌对、空闲和无未决动作/对话/预留冲突；UI 禁用不足以代替引擎拒绝。叙事加入如源于对话回答，只在已落盘选择后的安全边界执行，重复回调或过期选择不得招两次。
- 同 actorId 原子交接 HP/状态/装备/库存/growth/needs/计时/来源；成功可以更换实体表示但不得复制所有权，须使所有存活引用指向正确 owner。失败保留旧活对象身份、完整对象图、双 RNG、allocator、世界根及录制前缀。中途抛错分别注入每个写阶段，不只测输入预检失败。
- 身份切换不回血、补饱、重置冷却/装备授予，不重复成长/剧情奖励。怪物原生能力→受控能力有逐字段映射/白名单，不靠把 `ActorFacts.player` 全局改 true。无法无损承载的类型明确不可加入，给 i18n 原因。
- 加入/离队使旧计划、目标选择、预演、AI companionOrders、临时托管、已见敌人/预警记忆及录制异步 job 的适用性重新检查。取消尾部不能取消已支付的进行中动作；建议仅在无进行中动作的安全规划边界接纳转换（PD3）。新成员不自动追加到已提交窗口，也不继承前 owner 控制者权限。

### 2.2 三类来源和营地双向交接

| 入口 | 权威事实、成功结果与失败保护 |
| --- | --- |
| 已救俘虏→成员 | 先通过原生救援路径解除俘虏状态并建立可追溯来源，再显式升格；未救/敌对/临时/raid/body 子实体拒绝。原生同伴与受控成员的枚举/行动去重，原 companion order 撤销，合法 ID 与物品保持。普通召唤不能冒用救援来源。 |
| 叙事 NPC→成员 | 用现有 NPC 实例、剧情事实及已审招募白名单；不把所有“对话完成”都当同意。取消/不合资格/满员不得消费一次性招募事实或重发奖励；成功后该实体不会同时留在原层当可再次招募的 NPC。往返居民后仍保留故事身份及已有收据。 |
| 居民→成员 | 先在事务内结算到当前世界时点，再从真实居民根移交：营地归属、床位、岗位、工作票据、库存 escrow/退款、材料预留、订单/劳动引用、需求/日粮及离营事件。按原 owner 合同释放/归还，不丢货不复制。未完成且不能安全结算的工作明确阻挡；不是先删 resident 再尝试加 roster。 |
| 成员→居民→成员 | 营地合法、床位和居民资格可用；主成员限制按 PD1。解除 party 控制/计划与成员时钟，接入原居民经济、日粮、工作与离营机制；重新编入时停止居民离线账，恢复受控身份。居民可在非活动层按 world5 经济运行，普通留守成员继续冻结，不能两边同时计饥饿/劳动。 |

在当前层、离层/恢复、营地拆除/床位不足、死亡/全灭、leader 转换、库存超容量、忙碌/待决/异步 flush 等状态明确结果。首版建议只允许同活动层当面操作，先召回留守者再派驻，不开远程转换；玩家能看见“留守冻结”和“派驻居民持续生活”两种不同状态。

### 2.3 UI 与创建

- 成员栏同时显示生命、活动/留守/居民来源、控制方式、忙碌和计划摘要；切焦点不改变世界或随机流。居民名册提供编入按钮，小队名册提供派驻入口；俘虏/叙事现场提供可发现的加入入口和失败理由。满员不隐式替换、解散或丢弃成员。
- 地图计划层区分成员、已提交路径/目标与未提交草稿，显示过期/受阻/未知区域；只用合法已知投影，不泄露隐藏敌人、剧情资格或地形。预演仍是不确定预测，取消/改草稿/看路径对主局无副作用，正式提交重新验权。
- 320/390 竖屏：横滑成员条、地图与单行推进控件、抽屉编辑队列/旅行/AI/反应；横屏及桌面保持目标选择/背包/对话可用。切成员不能把旧地图回调发给新 actor；拖地图、点路径、按钮和关闭抽屉要区分手势。窗口待决必须突出真实执行者；托管/临时接管/硬停状态准确。
- 真实 MainMenu 动态模块发现、1/2/4 人 roster、可选 growth 身份及一次批量初始化保持；取消/重试/双击/异步旧回调不多发 new-game。无 growth/loot/narrative/settlement 时降级清晰，缺模块不出现空悬入口。玩家可见文本全部 i18n。

### 2.4 持久化、录像与删除

新增名册/来源/转换事实必须贯穿有效 manifest/规则身份、snapshot 联合校验、recording/header/inputState/origin、event/full digest、生产 Worker 冻结 job、seek/续录与失败回滚；Game 新字段登记 U03，写集及摘要字段同步显式登记。无 party 不新增 own keys、默认空根、版本/模块指纹变化，也不靠删字段归一化或重录旧黄金伪造零影响。

转换是一次可验证公开事件；重复/无效输入不留半个 roster，不增 RNG/时间/前缀。存读含转换前后、对话安全边界、居民离层经济及恢复；动态 roster 输入重放恰好一次。保留 256 固定 full、2048 chunk 与语义段末 full；保存续录只撤销允许撤销的临时末行 full。旧 party 格式明确拒绝、保活局，不迁移。物理删包要用本步实际转换后的档/录像验证缺包拒绝。
