# 小队与多人联机设计稿（草案）

> 状态：**设计稿待审**（2026-10-08，Claude 起草）。分支 `ext/party-design`，基于 `ext/phase5` `769f6fc`。只写文档，不改代码。
> 定位：新的扩展方向，不改变 Brogue「同步回合制、按 tick 结算」的底层规则；先做**单机多人小队**，再在其上做**回合制联机**。实施排在阶段 5 收尾（5Z）之后，避免与阶段 5 主线争抢 `Game.ts` / `TimeCoordinator.ts`。

---

## 1 目标与非目标

**目标**
1. 单机小队：玩家一人控制多个角色；每个周期可随时切换角色下达行动目标，统一推进；任一角色可交给 AI 托管，随时人工接手。
2. 窗口推进：以可调的 tick 窗口为周期推进世界；窗口内各角色按原生速度规则行动（快者多动、慢者一个动作可跨窗口）。
3. 节奏切换：简单内容用大窗口 + AI 托管快速度过；机关、混战、Boss 战切到小窗口甚至逐动作的精细操作。
4. 联机合作：多名玩家各控自己的角色，按「房主手动 / 全员准备 / 投票 / 倒计时」等规则提交窗口；同步建立在既有确定性与录像校验之上。

**非目标（本设计不做）**
- 实时制（不走 MAngband 式固定时钟）；PvP；大规模 MMO；跨版本联机。
- 改变原生速度、伤害、生成等规则数值（平衡调整只通过本扩展自己的缩放参数）。

## 3 核心概念

- **小队（Party）**：1–N 个**受控角色（Member）**，共享阵营与可见信息，属于同一局。N 上限见 D-02。
- **控制者（Controller）**：每个成员有一个控制者——`local:<玩家槽>`（人工）或 `ai:<策略>`（托管）。单机时所有人工控制者都是同一个玩家；联机时为不同玩家。
- **焦点（Focus）**：界面当前查看/下令的成员。焦点只影响显示与输入路由，**不进入规则与摘要**。
- **计划（Plan）**：成员在本窗口的行动目标：单个动作、动作队列、移动目标、或「交给 AI」。
- **窗口（Window）**：一次推进的 tick 长度 `W`（例如 100–1000）。窗口内世界照原生调度推进到 `W` 耗尽或被打断（§4.4）。
- **推进触发（Advance trigger）**：决定「何时开始结算下一个窗口」的规则；**只影响何时提交，不影响模拟本身**。

## 4 时间模型：在原生 tick 调度上开窗口

### 4.1 原生基础（不改）
Brogue 本身按 tick 调度：每个生物按移动/攻击速度累积 `ticksUntilTurn`；`TimeCoordinator` 推进到最近的行动者；阶段 3 的动作调度器（`run.actorActions`）已支持跨多个 tick 的阶段性动作（前摇/判定/后摇）。窗口制只是**在玩家行动点上加一层「是否暂停等待输入」的判断**，不改变任何生物的行动先后与耗时。

### 4.2 窗口内的成员行动
- 窗口开始时，所有人工成员已提交计划（或沿用上一窗口的未完成队列）。
- 推进中，当某成员到达自己的行动点：
  - 有计划 → 取下一步执行（与玩家亲自输入同一条命令路径，同样记录进录像）；
  - 无计划且由 AI 托管 → AI 选择动作；
  - 无计划且人工控制 → 默认「原地等待一个行动单位」（D-05 可改为「立即打断」）。
- 快速成员在一个窗口内可能行动多次；慢速成员的长动作可跨越窗口边界，下个窗口继续（已有调度器支持）。

### 4.3 窗口长度
- 预设档位：**精细（单动作）/ 短（100）/ 中（300）/ 长（1000）**，可由房主或单机玩家随时切换（D-03）。
- **自动档**：无敌对可见、无危险地形时自动用长窗口；任何打断条件触发后自动降到短窗口，直到 N 个窗口内无威胁再恢复（参数可配置）。

### 4.4 打断规则（关键）
窗口在以下任一情况提前结束，回到规划阶段（参考 Frozen Synapse 的「看见敌人的默认反应」与自动探索遇敌即停）：
1. 任一成员**首次看见**新的敌对生物（与现有自动探索的停止条件一致）；
2. 任一成员受到伤害、获得负面状态、HP 低于阈值；
3. 成员计划失效（目标消失、路径被堵、物品被拿走）；
4. 战斗预警（阶段 3 telegraph）指向任一成员；
5. 剧情/对话/确认框需要人工回应；
6. 成员到达楼梯、陷阱提示等需要决策的地点。
每个成员可设置「默认反应」（继续计划 / 停下 / 交给 AI 处理本窗口），减少无意义打断。

### 4.5 推进触发（单机与联机通用）
| 模式 | 规则 | 适用 |
|---|---|---|
| 手动 | 玩家/房主按「推进」 | 单机默认 |
| 全员准备 | 所有人工控制者都点了「准备」才推进 | 联机默认 |
| 投票 | 过半准备即开始倒计时 | 人多时 |
| 倒计时 | 每窗口限时，超时未提交的成员按 AI 或等待处理 | 快节奏 |
| 动作完成自动准备 | 成员计划非空即视为准备 | 托管为主时 |

### 4.6 局部节奏（参考 Soul Warden，联机阶段再启用）
联机时若成员分散在不同区域：以「是否处于同一威胁区域」分组，同一组共享窗口推进；不同组的窗口**在世界时钟上仍必须一致**（因为世界只有一个时钟）。因此局部节奏的实现方式是：没有威胁的组允许「预先提交多个窗口的计划」（排队），由威胁组的节奏驱动统一推进，而不是各自独立时钟。真正独立时钟（异步）属于 §7.7 备选。

### 4.7 预演
利用确定性与 seek：在规划阶段可「试推进」本窗口并显示结果，然后回滚（不记录、不影响 RNG 主流）。预演只对己方已知信息可靠（与 Frozen Synapse 一致，假设敌人不改变行为）；联机时预演只在本地运行。

## 5 单机小队模型

### 5.1 现状审计（初步数字）
`ext/phase5` 中直接引用 `this.player` / `game.player` 约 **2200 处**：`src/engine/Core` 1272、`src/ext` 859、`src/components` 40、`Combat` 32、`Map` 24、`UI` 10。P0 步骤需把它们分类为：
- A **镜头/显示**（视野渲染、消息视角、侧栏）→ 改读「焦点成员」；
- B **全队共享**（阵营判定、敌对关系、楼层进入）→ 改读「小队」；
- C **按成员**（背包、饥饿、状态、经验、装备、死亡）→ 改为对每个成员；
- D **唯一主角语义**（游戏结束、胜利条件、存档元数据）→ 改为「小队全灭」等规则。

### 5.2 实现策略
- 保留 `player` 作为**队长/主成员**（兼容大量现有代码与经典模式），新增 `party.members[]`，其他成员是带 `controlledBy` 标记的生物。
- 渐进迁移：先让非主成员「像盟友一样存在、但接受计划」，再逐步把 C 类机制（背包、饥饿、拾取）推广到成员。
- 经典模式与未启用小队的扩展局：`party` 不存在，零影响（对象形状、RNG、快照字节不变——沿用阶段 1–5 的零影响合同）。

### 5.3 规则口径（需决定，见 §15）
| 机制 | 推荐 |
|---|---|
| 视野 | 全队共享视野并集（D-06） |
| 物品鉴定知识 | 全队共享（同一局知识） |
| 背包 | 每人独立背包，相邻可交换（交换耗时） |
| 饥饿 | 每人独立（与 foraging 同伴饥饿统一组件，见 §10） |
| 经验/成长 | 每人独立 growth 状态；击杀经验按参与分配（D-08） |
| 死亡 | 成员死亡不结束游戏；全队死亡才结束；可设置「队长死亡即结束」变体 |
| 上下楼 | 只有全员在楼梯附近（或选择留下）才可换层；留下的成员进入离场层冻结（借用 world5 离线机制）（D-07） |
| 招募 | 来源：开局创建、救出俘虏、叙事 NPC 加入、营地居民编入（D-09） |

### 5.4 与「同伴」的区别
Brogue 原生盟友（俘虏、召唤）仍是「同伴」：由 AI 控制、不能下计划（或只能接受队长指令 §6.3）。「成员」是可完全操控的角色。同伴可被升格为成员（D-09）。

## 6 AI 托管

### 6.1 v1：战术档位（参考宝可梦不可思议迷宫）
每个成员选一个档位：**跟随队长 / 积极进攻 / 保持距离（远程）/ 只自保 / 不动**；附开关：自动拾取、使用消耗品阈值、避开危险地形。复用现有盟友 AI 与自动探索、自动行走逻辑。

### 6.2 v2：规则表（参考 Gambit）
有序「条件 → 动作」规则（如「HP<30% → 喝治疗药」「目标在射程内 → 射击」），条件与动作从白名单中选，数量上限 8–12 条；与 v1 档位并存（档位是预设规则表）。

### 6.3 队长指令（参考 BG3 UTAC）
不收回控制权也能引导：集合、攻击某目标、守住某格、撤退到某点、自动探索本层。对托管成员与原生同伴都有效。

### 6.4 接管与托管切换
任意时刻切换；切换发生在成员下一个行动点，不打断进行中的多 tick 动作（除非该动作允许取消）。切换本身是记录命令（零耗时）。

## 7 联机

### 7.1 架构：房主权威 + 命令锁步
- 房主运行完整模拟；客户端也运行同一确定性模拟（不传整个世界状态）。
- 每个窗口：各客户端发送自己成员的计划 → 房主按推进触发收齐后广播「窗口命令批次」（含序号与所有计划）→ 各端执行同一批次。
- 每个窗口结束交换**摘要**（复用阶段 5 录像 v4 的分域摘要）；不一致即判定不同步，房主下发快照纠正，并记录诊断（定位到窗口区间——与已批准的「首个可验证分歧 + 区间」口径一致）。
- 回合制对延迟容忍度高：窗口间隔本就以秒计，几百毫秒网络延迟无感。

### 7.2 可见信息
各端都有完整世界（锁步的代价），理论上可作弊看图。合作模式可接受（D-12）；若要防作弊需改为房主权威 + 只下发可见状态（成本高，不推荐首版做）。

### 7.3 房间与生命周期
创建房间（房主选种子与模块）→ 加入（版本、模块组合、规则指纹必须一致，否则拒绝）→ 分配成员 → 开局 → 窗口循环 → 存档（只有房主存，客户端可下载副本）→ 结束。

### 7.4 断线与重连
断线成员自动转为 AI 托管或「等待」（D-13）；重连时房主发送最近快照 + 之后的窗口批次，客户端快速重放追上。

### 7.5 中途加入/离开
加入者接管一个空闲成员或新建成员（D-14）；离开者的成员转托管。难度缩放按「当前人工控制者人数」或「成员数」（§9）。

### 7.6 基础设施（需产品决策 D-15）
GitHub Pages 只能托管静态页面，需要至少一种在线服务：
| 方案 | 说明 | 成本/复杂度 |
|---|---|---|
| WebRTC P2P + 轻量信令 | 房主即服务器；信令可用免费/低价服务 | 低成本；NAT 穿透失败时需 TURN 中继 |
| WebSocket 中继（如 Cloudflare Durable Objects / 小型 VPS） | 所有消息经中继转发 | 稳定、需运维与费用 |
| 托管游戏后端服务 | 第三方实时服务 | 依赖供应商 |
推荐首版：WebRTC P2P + 信令，失败回退到 WebSocket 中继。

### 7.7 备选：异步汇合（参考 rogOut）
各玩家独立推进自己的时间线，只在同一楼层/区域相遇时进入共享窗口。实现复杂（需要合并时间线、处理一方已改变世界），建议作为远期研究，不进入首版。

## 8 存档、录像与确定性

- 窗口命令批次就是录像事件的一种（新事件类型「窗口批次」：窗口长度 + 各成员计划 + 推进触发信息）。单机与联机共用。
- 预演（§4.7）不写录像、不影响 RNG 主流；AI 决策只读确定性状态并使用派生抽样（5A4 H4 的方式），不消耗原生 RNG，保证各端一致。
- 焦点、界面状态、计划草稿不进摘要。
- 版本：小队能力进入底座时升 foundation；联机协议有独立版本号，与模块组合、规则指纹一起握手校验。

## 9 平衡

- 数量优势：怪物 HP/伤害/数量按成员数缩放（参考 Stolen Realm 自动缩放），缩放表可配置；或限制小队规模（D-02）。
- 资源：每层物品数量是否随人数增加（D-10，推荐小幅增加消耗品、不增加稀有物）。
- 经验：按参与分配，避免全队等速成长（D-08）。
- 饥饿：每人独立，与 foraging 和营地粮食经济自然衔接（食物压力随人数上升）。

## 10 与现有系统的关系

| 系统 | 关系 |
|---|---|
| combat（阶段 3） | 预警、弹反、篝火按成员生效；篝火休息需全员或按成员（D-11） |

| loot（阶段 6） | 掉落分配规则（个人掉落 / 共享掉落 / 队长分配）（D-16） |
| 射击原型 | 无直接关系；仅可共享纯核心（数据、RNG、loot 生成器） |

## 11 UI

- 成员栏：头像/状态/计划摘要/控制者标识，点击切换焦点；手机端为底部可横滑条。
- 计划层：在地图上显示每个成员的计划路径与目标（参考 Frozen Synapse 路径点）。
- 推进控件：窗口档位、推进/准备按钮、倒计时、投票状态。
- 打断提示：明确显示打断原因并高亮相关成员。
- 托管设置面板：档位、开关、（v2）规则表编辑。
- 320/390 宽度：成员栏 + 地图 + 单行推进控件；计划编辑用抽屉。

## 12 模块边界

- **底座（foundation）**：小队与成员数据结构、焦点与输入路由、窗口推进与打断框架、窗口批次录像事件、按成员机制的通用改造。属于引擎级改造，本地 Codex 实施。
- **`party` 模块**：战术档位与规则表、队长指令、招募来源、平衡缩放、UI。可独立删除（删除后底座退化为单人）。
- **`netplay` 层**：房间、传输、握手、同步校验、重连。建议作为**产品层**（与扩展模块平级的独立入口或可选包），不进入规则摘要。
- 删除合同：删除 `party` 后经典与其他扩展局零影响；删除 `netplay` 后单机小队照常。

## 13 分步计划

## 14 风险

1. **单人假设迁移量大**（约 2200 处）：P0 必须先做透，否则 P1 会反复返工。
2. **玩法定位冲淡**：Brogue 的单人资源博弈与潜行会被多角色削弱；需要缩放与「小队规模上限」配合，并保留单人模式。
3. **手机界面复杂度**：多成员管理在 320/390 宽度上难做好；P1d 必须早做原型。
4. **打断规则调校**：过于敏感会频繁停顿，过于迟钝会让成员白白受伤；需要可配置并收集试玩反馈。
5. **联机基础设施成本与运维**：需产品决策。
6. **AI 质量**：托管 AI 若添乱（挡路、乱用消耗品），会让「托管度过垃圾时间」失去意义；v1 宁可保守。
