## 总原则

1. **规则服务于新产品，不要求对齐 CE。** 可直接修改引擎、战斗、生成、内容和数值，不要求 classic 路径、JSON 投影、骰子顺序或行为逐字节不变。无需为了保护 classic 复制求值器或绕策略端口；现有 `resolveAttackExtended` 等分支可在后续需要时合并、重构，本次不实施。
2. **测试保护当前设计，不冻结旧玩法。** 取消经典隔离/零调用证明及 classic/extended 中性战斗对等测试的长期维护义务。有意改变规则时，可相应修改或删除已失效的相关测试，并在报告中说明改动、原因和仍保留的覆盖；无需逐项请示，也不要求单变量反事实。这不授权随意削弱全部测试、掩盖非预期回归或默认立即删除现有测试；有效的功能、边界、状态一致性和录像测试仍应维护。
3. **暂时保留扩展内部的确定性录像。** 所有改状态输入仍经 `game.executeCommand` / `executeItemCommand`，规则随机数走引擎 RNG，纯显示不消耗实质随机流。目的是让复杂系统的 bug 可复现、可调试，直到维护者另行决定；不要求新规则重放旧规则版本的录像，也不要求与 CE 逐骰一致。存档/录像与规则数据的版本校验继续保留。
4. **保持有用的模块化，不为隔离绕路。** 模块仍可使用 `src/ext/modules/<模块>/`、通用组件、生命周期、命令和数据定义；引擎规则与接入方式可按需求直接重构，不强制所有变化只能经过钩子/策略端口。现有只读 DTO、受控提交与资源所有权等合同在相应实现改造前仍有效，不能借普通事件回调偷偷修改世界。
5. **玩家与 NPC 共享规则。** 等级、属性、职业、种族、信仰、技能等继续采用通用生物组件与共享实现，而不是玩家专属字段（见 `references/totalwar-notes.md`）。
6. **按需吸收 main 的通用修复。** 通用 UI、输入和性能修复可按需要通过 merge 或 cherry-pick 纳入本分支；不适合原型的改动可以舍弃，不要求持续对齐 main。当前没有将本分支合回 main 的计划。

## 阶段 2–5 的独立模块目标合同

以下是后续实现必须达到的目标，**尚未全部实现或验收**；阶段 2 的设计与分步落地计划见 [叙事设计](phase2-narrative.md)，现有耦合与通用边界见 [架构 §16](architecture.md#16-阶段-25-独立组合与可移除性目标)。

- 每个阶段使用独立且稳定的 module ID、`src/ext/modules/<moduleId>/` 目录、独立数据包及版本、独立存档命名空间，以及录像 manifest 中该模块自己的版本/规则数据标识；阶段 2 使用 `narrative`
- 只硬依赖底座，不硬依赖 growth 或其他阶段模块。开局可自由选择模块子集；单独启用、任意组合及不启用这些模块时，其余游戏均须正常游玩、存档与录像回放。一局内模块集合仍固定，存档/录像按其精确 manifest 校验
- 模块联动仅通过可选软接口；对方未启用时跳过联动或使用明确的替代行为，不能因缺少可选模块而报错。不能通过隐式要求 growth 组件、导入另一阶段规则文件或捆绑必选 UI 来实现联动
